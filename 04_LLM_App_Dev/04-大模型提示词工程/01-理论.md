## 一、提示词工程是什么

提示词工程（Prompt Engineering）的核心就是指“我们该给大模型发送什么内容，以便大模型能更符合我们期望地完成任务”。

## 二、提示词怎么写

> 首先要记住：**没有完美的提示词、我们也不需要完美的提示词，我们只需要能解决问题达成期望的提示词**
>
> 其次要记住：
>
> * **我们很难通过一次尝试就得到完全符合期望的提示词，所以如果我们大概知道第一版提示词该怎么写那就大胆写出来，先完成后完善；而如果我们连第一版提示词都不知道该怎么写，那就直接告诉 AI 我们的目标，让 AI 来给我们生成或反推得到第一版提示词**
> * **接下来我们就是拿着提示词不断地跟大模型聊天，来看看它的输出到底符不符合我们的期望，一遍一遍地告诉 AI 提示词哪里不符合预期以及我们的预期效果，让 AI 来针对性地优化提示词，直到符合我们的期望为止**

```markdown
## 角色 必备⭐️⭐️⭐️⭐️⭐️
......

## 背景 必备⭐️⭐️⭐️⭐️⭐️
......

## 目标 必备⭐️⭐️⭐️⭐️⭐️
......

## 约束 必备⭐️⭐️⭐️⭐️⭐️
......

## 步骤 推荐⭐️⭐️⭐️

......

......
```

#### 1、Role（角色）

**用途**

**角色用来给大模型立人设，决定了大模型推理时站在谁的角度思考问题、知识范围与专业程度、语言风格等，就像我们给新员工明确自己的角色定位一样。**没有角色的话，大模型会调用平均水平的知识回答；有角色的话，大模型会优先采用对应领域的知识体系、术语和思维方式。

例如同样问一句：我的产品为什么卖不出去？

不同角色回答完全不同：

- 产品经理：分析需求、用户和功能。
- 市场营销专家：分析流量、品牌和渠道。
- 投资人：分析商业模式和增长潜力。
- 心理咨询师：分析你的情绪和认知。

**案例**

```
角色：
你是一位拥有 15 年经验的互联网产品经理专家，擅长 AI 产品设计、商业分析和用户增长。
```

#### 2、Background / Context（背景 / 上下文）

**用途**

**上下文用来给大模型提供背景信息，就像我们给新员工讲一讲要接手的项目背景一样。**很多问题没有背景，大模型根本不知道应该按照什么标准回答；背景越完整，回答越贴近真实情况。

例如同一句：推荐一个创业项目。

不同背景回答完全不同：

* 大学生：可能推荐校园项目。
* 全栈程序员：推荐 SaaS。
* 宝妈：可能推荐母婴内容。

**案例**

```
背景：
我是一个拥有 10 年经验的全栈开发者，目前在一家 AI 公司负责 AI 产品。
目标是在一年内做出一个能够月收入 10 万元的 AI 产品。目前团队只有我一个开发者。
```

#### 3、Goal（目标）

**用途**

**目标用来告诉大模型到底要干什么，就像我们给新员工说下要干什么一样。**没有目标的话，大模型就会胡乱猜测我们的目标，导致答非所问；目标越具体，结果越稳定。

**案例**

不好的目标

```
目标：
请分析这个 AI 产品。
```

很好的目标：

```
目标：
请分析这个 AI 产品是否具有商业化价值，并分别从市场需求、竞争情况、盈利模式和实施成本四个维度进行分析，最后给出是否值得创业的建议。
```

#### 4、Constraints（约束）

**用途**

**约束用来告诉大模型不应该干什么，就像我们给新员工定点禁令、别多事、别乱搞一样。**大模型默认喜欢补充信息、发散回答，猜测缺失内容；添加约束可以限制大模型的自由发挥，避免引入不必要的麻烦。

**案例**

```
约束：
- 不允许编造事实。
- 如果信息不足，请及时反馈，别闷着憋到 deadline 再问我，早发现早预防。
- 使用中文回答。
- 不要输出 Markdown 表格。
- 回答控制在 500 字以内。
```

#### 5、Process（步骤）

**用途**

**步骤用来告诉大模型按什么步骤执行，就像我们给新员工说下某个活具体该一步一步怎么干一样。**没有步骤，大模型可能快速执行直接给结论，可能不满足我们的期望；有步骤，大模型更容易做到分析完整、逻辑清晰，结果也更容易满足我们的期望。

**案例**

```
步骤：
第一步：总结需求。
第二步：分析问题原因。
第三步：提出三种解决方案。
第四步：比较优缺点。
第五步：推荐最佳方案。
```

#### 6、Output Format（输出格式）

**用途**

**输出格式用来告诉大模型最终输出长什么样，就像我们让新员工每干一个活就沉淀一些特定格式的文档一样。**如果不给输出格式，大模型每次输出可能都不一样；给了输出格式，大模型每次输出稳定，方便阅读、方便程序解析、方便后续自动化。

**案例**

```
输出格式，以 JSON 的形式：
{
    "score":0,
    "reason":"",
    "suggestion":""
}
```

#### 7、Example（示例）

**用途**

**示例用来帮助大模型更容易理解我们的诉求，就像我们给新员工举个例子，更形象直白、更容易理解。**很多时候，解释半天，不如给一个例子，大模型会自动学习示例中的模式。

**案例**

```
示例：

输入：今天心情很好。
输出：积极
------
输入：服务太差了。
输出：消极
```

#### 8、Evaluation（验收标准）

**用途**

**验收标准用来告诉大模型执行完成以后，自己检查一遍，就好像我们让新员工自测一样。**很多大模型回答不是不会，而是漏回答、忘记遵循格式、偶尔出现逻辑遗漏，增加验收标准，相当于让大模型在交卷前先自己检查一遍，通常可以提高完整性和一致性。

**案例**

```
验收标准，输出前请检查：
- 是否遗漏了任何一个分析维度。
- 是否存在事实错误。
- 是否严格按照指定格式输出。
- 如果发现问题，请先修正，再输出最终结果。
```
